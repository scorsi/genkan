# ADR 0003: Reload on SIGHUP, keep the running config on failure, readiness via sd_notify

## Context

The config is generated by Nix and replaced atomically on `nixos-rebuild
switch`. Certificates on disk are rewritten by sops-nix and hanko on their own
schedule. genkan must pick up both without a restart, and a bad
config must never take the whole homelab offline: every service is behind
this one process.

## Decision

1. **Reload trigger: SIGHUP only.** No file watching. The NixOS module sets
   `ExecReload`; `sops.secrets.<name>.reloadUnits` and hanko's reload list
   point at `genkan.service`.
2. **On SIGHUP** genkan parses and validates the new file, loads certificates,
   binds any new listeners, then swaps routes, certificates and listeners
   atomically. Listeners whose address disappeared are closed.
3. **If the new config fails** at any step, genkan keeps running on the
   previous config and logs at `ERROR`. It never exits on a failed reload.
   At startup an invalid config is fatal.
4. **Two upstream guards** make the runtime case rare:
   - **Build time:** the NixOS module runs `genkan validate` on the generated
     TOML inside a derivation. An invalid config does not produce a system to
     activate.
   - **ExecReload:** `genkan validate <config> && kill -HUP $MAINPID`. A
     validation failure makes `systemctl reload` fail and surfaces in the
     `switch` output.
   `validate` checks structure, references and uniqueness (listener names,
   hosts, certificate names, addresses). It cannot open certificate files at
   build time because they are secrets; file checks happen at load.
5. **Readiness via sd_notify.** genkan writes `READY=1` to `NOTIFY_SOCKET`
   once all listeners are bound; the unit uses `Type=notify`. Stdlib only.
6. **Connection draining is out of scope for v0.** A reload swaps the routing
   table; in-flight connections continue on the handler they already have and
   are not tracked. Listeners removed by a reload are closed immediately,
   which drops their in-flight connections. Draining can be added later
   without a config change.

## Alternatives considered

- **Crash on invalid reload.** Proposed initially on the grounds that the old
  config no longer exists on disk. systemd would restart genkan against the
  same invalid file, crash-loop, hit `StartLimitBurst` and stop. One typo in
  Nix takes down the forge and everything else. The in-memory config is still
  valid, so keeping it costs nothing and degrades gracefully. Rejected.
- **File watching (fsnotify).** More code, a dependency, and the atomic
  rename dance Nix uses defeats naive watchers. SIGHUP is what the Nix
  integration points already emit. Rejected.
- **HTTP `/healthz` for readiness.** No consumer exists today; sd_notify is
  fewer lines and gives systemd real ordering information. Kept as a proposal
  for an admin listener alongside metrics (v1+).

## Consequences

- Every reload-related failure is visible in `nixos-rebuild switch` output,
  either at build or at `systemctl reload`.
- A config that is valid but cannot be applied (port already in use) is the
  only case that reaches the runtime fallback; it is logged, the service stays
  up on the old config, and a later restart would fail at startup.
- Dependent units can `After=genkan.service` and trust it.

### 2026-10-21: Session resumption

Reloads preserve TLS sessions when the SNI remains configured with the same
leaf certificate; removed names fail TLS, and changed certificates require a
full handshake. Ticket keys rotate independently of reloads using Go defaults.
See [ADR 0010](0010-reload-safe-session-resumption.md) for the binding and
key-lifetime trade-offs (implemented for owner review).

## Status

Accepted, 2026-10-12.
